Dimension 02

Stable Identity & Structural Parsing

How do you give text permanent addresses — and keep them through edits, moves, and copy-paste?

❓

The Question

This is the core primitive. Every other capability — annotations, transclusion, provenance — depends on stable identity. If you can't stably reference a paragraph, you can't annotate it. If you can't stably reference a sentence, you can't transclude it. The entire runtime rises or falls on this one decision.

The question breaks into three sub-questions: (1) What kind of identifier? (2) At what granularity? (3) How does it survive edits?

🔑

What Kind of Identifier?

Purple Numbers (2001) defined the crucial distinction that every subsequent system adopted:

HIDs — Hierarchical Identifiers
Human-friendly · Break on move
Like 1.5.3 — encodes position in the hierarchy. Good for static, published documents where content doesn't move. Break when you insert a paragraph before position 3, or reorder sections. Useful as a human-facing convenience, but not as the primary addressing mechanism.
NIDs — Node Identifiers (UUIDs)
Machine-friendly · Survive everything
UUID v7 — time-ordered, globally unique, no coordination needed. Persist for the lifetime of the content. If a paragraph moves from section 2 to section 5, its UUID stays the same. This is the primary addressing mechanism for the runtime.
"Augment-style statement IDs (NIDs) are better references for dynamic documents, because even if an item's location changes in new versions of a document, the link will continue to point to the correct item." — Eugene Kim, Purple Numbers (2001)

The field converged on UUID v7 as the default. It's monotonically increasing (good for B-tree storage in SQLite), globally unique without a central authority, and familiar to every developer. Content hashes (like BendScript's CID) add integrity verification but can't re-anchor after edits — they're complementary, not a replacement.

🎯

At What Granularity?

This is the granularity problem — and every prior system hit it. Too coarse, and you can't annotate what needs annotating. Too fine, and the reference space explodes.

LevelStabilityPrecisionVerdict
Character Low — every keystroke changes identity Maximum precision UUID thrash. Every edit creates new sub-nodes. Not viable.
Word Low-medium — words change frequently High Too unstable. Word choice is the most edited aspect of text.
Sentence High — sentences are edited less often than words Good Primary granularity. Natural semantic unit. What humans quote, annotate, reference.
Paragraph Very high — paragraphs are the most stable unit Moderate Block-level identity. Good for structural operations (move, reorder, transclude).
Section/Heading Highest — rarely deleted Low Good for document-level navigation.

The recommendation: Sentence-level granularity as the primary addressing unit, with paragraph-level UUIDs for block operations, and character offsets for sub-sentence precision. Sentence detection is a solved problem — Santhosh Thottingal (2026) demonstrated a six-stage pipeline for HTML sentence segmentation using sentencex-wasm.

For cases where sentence detection fails (code blocks, poetry, bullet lists), fall back to the containing block as the addressable unit. The system degrades gracefully, never silently.

🔬

Four Approaches to Identity

The prior art reveals four distinct approaches to giving text stable identity. Each has different trade-offs, and the Text Runtime may need to compose several of them.

UUID-Based (Nominal Identity)
✅ Recommended · Notion, Tiptap, kaos-content
Every node gets a UUID v7 at creation time. The UUID is the node's name — it doesn't change when content changes. Parent references, backlinks, and transclusions all use the UUID. The SuperDoc paraId pattern adds a post-change hook that assigns fresh IDs to new nodes and deduplicates on split/merge.
Content-Hash Identity
⚠️ Complementary · BendScript, Web Verse
The node's identifier is a hash of its content (SHA-256 or CID). Self-verifying — you can detect if content changed. But renames and reorganizations break references. Good as a verification layer, not as the primary addressing mechanism.
Position-Based Identity
❌ Avoid as primary · ProseMirror native, XPath
Identity is derived from position in the document tree. Zero tooling cost. But edits invalidate positions immediately. Requires complex mapping layers (ProseMirror's step mapping, Hypothesis's position mapping). Fragile.
CRDT-Based Identity
🔄 Future-proof · Yjs, Automerge
Every character position has a permanent (clientID, clock) tuple. When content is inserted, positions are fixed forever. This is the most principled approach — permanent identity at every level. But CRDT documents grow unboundedly and need compaction for long-lived documents.
🌳

Structural Parsing: Text → Tree

The second half of the identity problem is parsing. Before you can assign UUIDs, you need to know what a "node" is. The Text Runtime parses text into a typed structural tree:

Document
├── Section
│ ├── Heading (h1)
│ ├── Paragraph
│ │ ├── Sentence
│ │ └── Sentence
│ ├── Blockquote
│ │ └── Paragraph → Sentence
│ └── CodeBlock
├── Section
│ ├── Heading (h2)
│ ├── List
│ │ ├── ListItem → Paragraph → Sentence
│ │ └── ListItem → Paragraph → Sentence
│ └── Paragraph → Sentence
└── Section ...

The parsing pipeline is format-specific at input, format-agnostic at output. Markdown uses remark/mdast. Plain text uses a sentence tokenizer. HTML uses tree-sitter. Each parser produces the same typed tree. New formats implement a Parser interface — the runtime doesn't care what format the text came from.

Critically, parsing is best-effort, never failing. Malformed Markdown doesn't crash the parser — it degrades gracefully, preserving as much structure as possible and recording uncertainty via confidence scores on each node.

⚙️

The UUID Assignment Pattern

SuperDoc's paraId allocator provides the canonical implementation pattern:

// After every document change, walk the tree
appendTransaction(transaction, oldState, newState) {
  // 1. Find new nodes (no paraId)
  // 2. Assign fresh UUID v7 to each
  // 3. Deduplicate (split: first half keeps old ID, second gets new)
  // 4. Handle paste (clone → new IDs to avoid collision)
  // 5. Return transaction with ID assignments
}

Key rules from prior art:

Split: When a paragraph is split into two, the first half keeps the original UUID. The second half gets a new UUID. This preserves references to the "before" content.

Merge: When two paragraphs merge, the surviving paragraph keeps its UUID. The absorbed paragraph's UUID is retired. References to the retired UUID enter active_partial state.

Copy-paste: By default, pasted content gets new UUIDs — it's an independent copy. When explicitly transcluding (not copying), the UUID is preserved — it's a reference to the same content.

Delete: The UUID enters a tombstone state. References to deleted nodes become orphans, shown with the last known content and a visual indicator. Never silently hide the break.

💡

The Key Insight

"Identity must be independent from position. Never identify something by paragraph 17 or sentence 9. Ordering is stored separately — it's a list of UUIDs, not a numbered sequence. Position changes should never invalidate identity."

This is the architectural invariant that enables everything else. When identity is independent from position, a paragraph can move from section 2 to section 5, and every annotation, transclusion, and reference to it survives. When identity depends on position (as in all current text editors), any structural change breaks all references.
