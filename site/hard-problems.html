Dimension 06

Hard Problems & Open Questions

What's still unsolved? What breaks every system that tries this?

❓

Why This Dimension Matters

Every prior system hit the same hard problems. Xanadu never shipped at scale. Purple Numbers polluted the reading surface. Hypothesis accepts that some annotations will always be orphans. Notion locked the solution inside a product. Understanding these problems before building is the difference between succeeding and joining the graveyard.

These are not implementation details. They are conceptual tensions — problems where the right answer depends on context, use case, and trade-offs that have no perfect resolution. The best we can do is surface them clearly, make explicit choices, and design mechanisms that work in the most common cases while degrading gracefully in the rest.

⚡

The Five Hard Problems

1
The Granularity Problem
At what level of granularity do you assign UUIDs? Too coarse (paragraph only) and you cannot annotate a sentence within a paragraph. Too fine (character level) and UUID thrash destroys stability — every keystroke creates new sub-nodes. Sentence is the right semantic unit, but sentence detection is imperfect for certain writing styles: code blocks, bullet lists, poetry, non-English text.
Approach: Sentence-level primary, block-level fallback. When sentence detection fails or confidence is low, fall back to the containing block as the addressable unit. Code blocks, tables, and list items are treated as atomic blocks. The system records its own uncertainty — a confidence score on every node tells consumers when to trust the parse and when to treat the node as approximate. Risk: Mis-split sentences create unstable annotation targets. Mitigated by: annotation selectors include both the sentence UUID (for when it exists) and the parent paragraph UUID (fallback).
2
The Transclusion Edit Problem
If document A transcludes a paragraph from document B, and a reader of document A wants to edit it — what happens? Edit in place (modifying source, potentially breaking other transclusions)? Navigate to source (safe but creates friction)? Create a fork (diverges from source, defeating transclusion's purpose)? This is not a technical problem — it's a policy and UX problem. The right answer depends on context.
Approach: Offer both modes explicitly. By default, transclusions are read-only — you see the content but cannot edit in place (Obsidian's model). When editing is enabled, surface backlinks before committing: "This paragraph is referenced by 3 other documents. Editing it will change those documents too." The user makes an informed choice. Risk: Users may not understand the difference. Obvious UI distinction between "this is a live reference" and "this is an independent copy" is essential.
3
The UUID Migration Problem
When text is copied from document A to document B, does the UUID follow? If yes, you have an implicit transclusion (changes propagate). If no, you have an independent copy (no connection). The only way to distinguish is user intent — and requiring users to declare intent ("is this a copy or a transclusion?") breaks flow. Yet guessing wrong means either unwanted coupling or lost provenance.
Approach: Copy-paste (Ctrl+C/Ctrl+V) generates new UUIDs — it's an independent copy. Explicit transclusion (a deliberate "embed by reference" action) preserves the UUID. The difference is signaled by the action, not by a dialog. For AI-generated text that derives from sources, use the derivedFrom provenance relationship instead of preserving the UUID — it's a new node with lineage, not the same node in a new context. Risk: Users accustomed to "everything is a copy" may be surprised when transclusions update. Documentation and progressive disclosure are essential.
4
The Re-Anchoring Failure UX Problem
After document edits, annotation re-anchoring can fail. What do you show the reader? Hypothesis shows states: active, active_partial, orphan. The LFCC mandates: "No silent drift — annotations MUST NOT silently reattach to unrelated content." But what does the reader actually see when a referenced paragraph is deleted? A placeholder? An error? The last known content with a warning? The UX of reference failure is central to the system's trustworthiness.
Approach: Every annotation carries an explicit confidence score (0.0–1.0). Active (≥0.95): no indicator — the annotation is where it should be. Active_partial (0.5–0.94): subtle dashed underline — "this annotation may not be at the right place." Orphan (<0.5): show the last known content in a visibly distinct container with a clear label: "This annotation references deleted content." The user can accept, adjust, or delete. Risk: Over-warning (too many active_partial indicators) trains users to ignore them. Calibrate thresholds based on real-world data.
5
The Annotation Ownership Problem
When paragraph X is transcluded from document A into document B, and someone annotates it in B — where does the annotation live? In B's annotation store (local to the transcluding document)? In A's (attached to the source)? In a shared overlay (visible from both)? What if the transclusion is removed — does the annotation disappear or become an orphan in B? This is the deepest unsolved question in the annotation-on-transcluded-content space.
Approach: Annotations on transcluded content live in the transcluding document's annotation store by default — they are annotations on a particular use of the content, not on the content itself. When the transclusion is removed, those annotations become orphans referencing a UUID from another document. They remain visible with a "transclusion removed" indicator. Shared annotations (visible everywhere the content appears) require explicit opt-in. Risk: The distinction between "annotating the content" vs. "annotating this use of the content" may confuse users. Default to local annotations; shared annotations as a power-user feature.

Open Questions

  • 1. Storage
    CRDT compaction for long-lived documents. Yjs documents grow unboundedly with edit history. For a persistent Text Runtime, we need a strategy for compacting history while preserving identity. This is an active research area with no production-proven solution. Can we snapshot identity at intervals and compact the edit history without breaking references?
  • 2. Cross-Document
    Cross-document annotation conflicts. When two documents annotate the same transcluded paragraph with conflicting claims (e.g., one says "this is accurate," another says "this is outdated"), how is the conflict surfaced? Does the reader see both annotations? Is there a conflict resolution UI?
  • 3. Scale
    Performance at scale. Hypothesis's content mapping phase takes "several seconds for longer documents." For a runtime that processes documents on every write, this is unacceptable. Can we make the mapping incremental — only re-map the changed portion? Can we cache UUID lookups so re-anchoring is O(1)?
  • 4. Format
    Round-trip fidelity. If we parse Markdown into a tree and project it back to Markdown, will the output match the input? Round-trip fidelity is critical for the runtime to be invisible. kaos-content has fuzz-tested round-trip serializers, but only for a subset of Markdown. Full CommonMark fidelity needs verification.
  • 5. UX
    The invisibility requirement. The runtime must be completely invisible during writing and reading — it must "be there when you need it and gone when you don't." How do we surface runtime capabilities (query this paragraph, see its provenance, check what references it) without breaking flow? Right-click? Keyboard shortcut? Side panel? This is a UX design problem, not a technical one.
  • 6. AI
    LLM-native annotation generation. Semiont's write-time selector reconciliation was designed for LLM-generated annotations. How do we handle cases where the LLM's exact text doesn't match the source (off-by-one whitespace, paraphrased quotes)? Do we accept approximate matches or reject them? The Semiont approach (reject, ask LLM to retry) may not work at scale.
  • 7. Scale
    The next conference problem. When the corpus grows from 90 talks to 500+, does the architecture hold? Manual enrichment that works for 90 documents doesn't scale to 500. The overlay system supports growth in principle, but automation (auto-tagging, auto-relationship detection) becomes necessary. At what point does the system require AI-assisted curation?

Why Prior Systems Didn't Win

Understanding these failures is as important as understanding the successes. Four patterns emerge:

1. Polluting the surface. Purple Numbers put identifiers in the text. Readers saw "¶ 1.5.3" before every paragraph. The numbers were useful but ugly — they broke the flow state. Lesson: Stable IDs must be invisible. The runtime layer must never contaminate the writing surface.

2. Requiring a global address space. Xanadu required every byte of text on the planet to have a permanent address, assigned by a central authority. Technically correct, economically impossible. Lesson: UUIDs with a document-scoped base URL are sufficient. Don't solve the global addressing problem — solve the local-first addressing problem.

3. Locking the solution inside a product. Notion proved block-level UUIDs and transclusion work at scale — but only inside Notion. You cannot use Notion's block model under your own editor. Lesson: The Text Runtime must be a library/runtime, not an application. It must work under any surface.

4. Over-engineering for a single use case. SiSU is a marvel of document engineering — parse once, emit many formats with stable citation numbers across translations. But it was built for one author's book publishing workflow. Lesson: Build for the general case. The runtime should be the operating system for text, not a single-purpose tool.
