Dimension 03

Annotation Overlays & Anchoring

How do annotations survive when the underlying text changes?

❓

The Question

Annotations are the first consumer of stable identity. Once you can reference a paragraph by UUID, you want to attach metadata — highlights, comments, tags, provenance records. But text changes. Paragraphs get edited, split, merged, moved, deleted. Annotations that don't survive edits are useless.

The prior art has a clear answer: applicative overlays with dual selectors and cascading fallbacks. This is the pattern that Hypothesis proved in production and that the W3C standardized. It works. The question is not whether to adopt it but how to adapt it for a runtime that has UUIDs (which Hypothesis didn't have).

📎

Applicative Overlays: Annotations Outside Content

The single most important architectural decision: annotations are never embedded in the text. They live in a separate overlay store and reference text nodes by UUID. This is what Xanadu meant by "applicative" links — applying from outside to content that is already in place with stable addresses.

"By this method it is possible to have thousands of overlapping links on the same body of content, created without coordination by many users around the world. The xanalogical content link is not embedded. It is applicative — applying from outside." — Ted Nelson, Xanadu (2000)

Embedded annotations (HTML-style <a href="..."> inside the text) have three fatal flaws: (1) only one annotation can occupy a given character range, (2) multiple authors' annotations conflict, (3) annotations pollute the text surface. Applicative overlays solve all three. The text stays clean. Annotations are stored separately. Multiple annotation systems — comments, highlights, provenance, AI-generated tags — coexist without coordination.

🎯

The Four-Strategy Cascade (Hypothesis)

Hypothesis's production anchoring system (2013, updated 2017) defined the canonical approach. When a document changes, annotations are re-anchored using four strategies in order. Each strategy is tried; if it fails, the next is attempted. If all four fail, the annotation becomes an orphan.

1
Fastest · Works 90%+ of the time
Exact UUID + Offset Match
Look up the target UUID. Verify the character offsets point to the same content. If the UUID exists and the text at the offsets matches, the annotation is confirmed. This is the fast path — it works when the document hasn't changed or has only had non-target edits.
2
Fast · Works when structure changes but content is stable
Character Offset (Global Position)
If the UUID-based lookup fails (node was split or merged), try global character offsets. Works when the document restructured but the text content is stable. Success = the text at the expected offsets matches the saved exact text.
3
Slower · Handles both structural and content changes
Context-First Fuzzy Matching
Search for the prefix (fuzzy, near expected position), then the suffix (fuzzy, near expected position), then verify the text between them against the saved exact text. Uses edit-distance-based acceptance threshold. This is the workhorse — it handles most real-world edits.
4
Slowest · Last resort
Exhaustive Fuzzy (Full Document Search)
Search entire document for the exact text. If found exactly once, re-anchor there with reduced confidence. If found multiple times, mark as orphan. Can produce false positives — confidence score must be below 0.8.
🔀

Dual Selectors: W3C Web Annotation Model

The W3C Web Annotation Data Model (2017) standardized the selectors framework. Every annotation stores multiple selectors that describe the same span from different angles. Semiont (AI Alliance, 2025) added the critical operational insight: reconcile at write time, verify at read time.

TextPositionSelector
Precise · Fragile under edits
{start: 245, end: 312} — character offsets from the start of the document. Fast to resolve, exact. But any edit before the start offset shifts everything. Best as the primary selector when combined with UUID verification.
TextQuoteSelector
Robust · Survives most edits
{exact: "text content", prefix: "...", suffix: "..."} — identifies text by its content and surrounding context. Robust to structural changes and most edits. The prefix/suffix disambiguates repeated text. The canonical fallback selector.
FragmentSelector
UUID-based · The Text Runtime's advantage
{value: "node-uuid"} — references a named fragment by its stable UUID. This is what the Text Runtime adds that Hypothesis and W3C didn't have. If the UUID exists, resolution is instant and exact. The UUID is the primary anchor; text selectors are fallbacks.

The Semiont insight: "The two selectors are not independent guesses — they are reconciled at write time so they describe the same span. A no-overlap invariant rejects any annotation whose selectors disagree." At render time, only verbatim matching is used — no fuzzy fallback. This prevents the silent corruption that plagues fuzzy-heavy systems.

🚦

Annotation States: The Local-First Collaboration Contract

The Local-First Collaboration Contract (LFCC, 2025) formalized the annotation state machine that every anchoring system needs:

active
Anchored with high confidence
active_partial
Anchored with reduced confidence
orphan
Cannot anchor; show last known
hidden
User-chosen to hide
deleted
User-chosen to remove

The LFCC's most important principle: "No silent drift: annotations MUST NOT silently reattach to unrelated content." Every annotation carries an explicit confidence score (0.0–1.0). Below 1.0, the UI shows a visual indicator. Below 0.5, the annotation shows a warning: "This annotation may not be at the correct location." The user can accept, adjust, or delete. Silence is the enemy.

✨

What the Text Runtime Adds

Hypothesis and the W3C model were designed for a world without stable identifiers. They had to anchor annotations to text in web pages that could change at any time, with no cooperation from the content. Their multi-strategy cascade was born of necessity — there was no stable anchor point.

The Text Runtime changes the game. Every node has a UUID. The annotation's primary selector is the FragmentSelector with a UUID. Resolution strategy 1 (exact UUID match) succeeds almost always — it only fails when the target node is deleted. The text-based selectors (TextQuoteSelector, TextPositionSelector) become fallbacks for post-deletion re-anchoring, not the primary mechanism.

This transforms annotation reliability. Instead of a 90%+ success rate on strategy 1 (Hypothesis's position-based approach), the Text Runtime has a ~99% success rate on strategy 1, with text-based fallbacks for the remaining 1%.

"With stable UUIDs, annotations don't need to play the re-anchoring game every time the document changes. The UUID is the anchor. The text selectors are insurance, not the primary mechanism."
