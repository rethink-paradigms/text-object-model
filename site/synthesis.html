Text Runtime: Complete Synthesis

Six dimensions, sixty years of prior art, thirty sources. Together they reveal a complete architecture for treating text as addressable, stable objects — invisible to the writer and reader, present when you need to query, annotate, reference, or track provenance.

📐

The Six Dimensions

01
The Convergent Pattern
Six prior systems independently discovered the same four-layer architecture: Human Surface → Parser Pipeline → Object Store → Overlays. The referential document model — documents as lists of pointers with stable UUIDs — is the architectural invariant.
02
Stable Identity & Structural Parsing
UUID v7 per node at sentence granularity. HIDs for humans, NIDs for machines. CRDT-based identity for permanent character-level addressing. Identity independent from position — the core primitive that enables everything else.
03
Annotation Overlays & Anchoring
Applicative overlays referencing UUIDs, never embedded. Dual selectors (precise + fuzzy) reconciled at write time. Four-strategy cascading re-anchoring with confidence scores. Orphan state shown, never hidden.
04
Transclusion & Provenance
Content by reference — the killer app for stable addressing. Three levels: read-only, write-through, bidirectional. Provenance via PROV-O ontology tracking every transformation chain. UUID-based transclusion survives renames and reorganization.
05
Architecture & Pipeline
Five-stage pipeline: Normalize → Parse → UUID Assign → Index → Overlay. Format-agnostic object model. SQLite local-first storage. Eight key architectural decisions. Ten lego pieces from proven prior art.
06
Hard Problems
Granularity, transclusion edit, UUID migration, re-anchoring failure UX, annotation ownership. These are what broke every prior system. Understanding them before building is the prerequisite to success.

Interaction Map: How Every Dimension Connects

Pattern ↔ Identity
Architecture meets Primitive
The four-layer stack defines where identity lives (Object Store, Layer 3). Stable identity defines what populates it. Without the pattern, identity is ad-hoc. Without identity, the Object Store is empty.
Pattern ↔ Annotations
Architecture meets Overlays
The applicative overlay pattern (Layer 4) is defined by the architecture. The annotation system is the first consumer. The architecture says "overlays are separate"; annotations show how to implement them.
Pattern ↔ Transclusion
Architecture meets Killer App
Transclusion is what makes the referential model worth building. UUID-based transclusion is the "why" behind content-as-reference. Without transclusion, the architectural complexity isn't justified.
Pattern ↔ Architecture
Vision meets Implementation
The pattern is the "what." The architecture is the "how." The pipeline (Normalize → Parse → UUID → Index → Overlay) is the concrete instantiation of the four-layer theoretical model.
Pattern ↔ Hard Problems
Theory meets Reality
The hard problems are where the elegant four-layer pattern meets messy reality. Granularity, copy-paste semantics, annotation ownership — these are the gaps between the theoretical model and the working system.
Identity ↔ Annotations
Anchor meets Annotation
UUIDs are the primary anchors for annotations. The FragmentSelector (UUID-based) is what the Text Runtime adds that Hypothesis and W3C never had. Identity quality directly determines annotation quality.
Identity ↔ Transclusion
Identifier meets Reference
Transclusion is UUID-based referencing. ![[doc-uuid#paragraph-uuid]] survives renames, reorganization, and edits because UUIDs don't change. The stability of the reference equals the stability of the identity.
Identity ↔ Hard Problems
Stability meets Edge Cases
The granularity problem (where do UUIDs stop?), the UUID migration problem (does copy-paste preserve UUIDs?), and CRDT compaction are all identity questions. The answers determine the runtime's stability envelope.
Annotations ↔ Transclusion
Overlay meets Reference
The annotation ownership problem — when paragraph X is transcluded into document B and annotated there, where does the annotation live? This is the deepest unsolved question at the intersection of these two dimensions.
Annotations ↔ Architecture
Consumer meets Pipeline
The overlay layer (Stage 5) is where annotations live. The dual-selector reconciliation happens at write time in the pipeline. The cascading re-anchoring happens at query time. Architecture defines the hooks; annotations consume them.
Annotations ↔ Hard Problems
Robustness meets Failure
The re-anchoring failure UX problem is about how annotations degrade. The LFCC's "no silent drift" principle and the confidence score system are the bridge between annotation theory and failure handling.
Transclusion ↔ Architecture
Feature meets Infrastructure
Transclusion resolution (fetch source node by UUID, render in target context) is an architecture-level concern. The three levels of transclusion (read-only, write-through, bidirectional) define the API surface.
Transclusion ↔ Hard Problems
Killer App meets Killer Problem
The transclusion edit problem is the hardest unsolved challenge. Who owns the edit when content appears in multiple contexts? Every approach (read-only, write-through, fork) has trade-offs. There is no perfect answer.
Architecture ↔ Hard Problems
Design meets Constraints
The architecture must be designed with the hard problems in mind. Round-trip fidelity, performance at scale, CRDT compaction — these inform pipeline design. The architecture is shaped by the problems it must survive.
Identity ↔ Architecture
Core meets Pipeline
UUID assignment (Stage 3) and indexing (Stage 4) are the architecture's identity infrastructure. The SuperDoc post-change hook pattern, UUID v7 format choice, and structural hashing are architecture decisions about identity.

Cross-Cutting Patterns

01
Separation of Concerns at Every Level
All six prior systems converged: separate content from structure, structure from presentation. Xanadu's three-way split (content, links, transclusions), SiSU's object abstraction, Notion's block model. This is the architectural invariant — the pattern that every successful system discovered independently.
📜 Xanadu · 📚 SiSU · 🧱 Notion · 🔗 BendScript
02
Applicative Structure
Nelson's key insight — structure applied from outside, never embedded — appears in every dimension. UUIDs are the addressing layer. Annotations are overlays. Transclusions are references. Provenance is metadata. Nothing is embedded in the human-facing text.
🔗 Ted Nelson · 📎 Hypothesis · 📋 W3C Web Annotation
03
References, Not Copies
Every dimension converges on UUID references as the connecting mechanism. The system's native reference type: a UUID to a canonical text node. Everything — annotations, transclusions, provenance — references those UUIDs. Nothing copies content. The source document is always authoritative.
🔗 Ted Nelson · 📎 Purple Numbers · 🧱 All Six Dimensions
04
Graceful Degradation
Every dimension needs degradation. Parsing degrades (low confidence, never crashes). Annotations degrade (active → active_partial → orphan). Transclusion degrades (read-only → orphan when source deleted). Identity degrades (UUID survives split; fails on delete). The system never fails silently.
📋 Hypothesis · 📜 LFCC · 🔧 kaos-content · All Six Dimensions
05
Invisibility
The runtime must be invisible during writing and reading. The text surface stays clean. UUIDs, annotations, transclusion references — all live in the machine-facing representation. This is what Purple Numbers got wrong and what the Text Runtime must get right: the writer's flow state is sacred.
📜 Purple Numbers (lesson) · 🧱 Notion · ✍️ Text Runtime Proposal

Core Tensions

Embedding vs. Overlaying
Should structural metadata (UUIDs, hashes) be embedded in the source text or stored in a separate overlay? Embedding is simpler (self-contained) but pollutes the text. Overlaying is cleaner (separate concerns) but requires synchronization. Nelson and the four-layer architecture pull toward overlaying.
Resolution: UUIDs and structural metadata live in the object store (SQLite), never in the source text. The source text is canonical. The object store is an index. Rebuilding the store from the source should always be possible.
Stability vs. Precision
Higher granularity means more precise annotations but less stable references. Sentence-level is the sweet spot, but the tension persists: every level below sentence (word, character) trades stability for precision.
Resolution: Sentence-level UUIDs as primary. Character offsets within sentences for sub-sentence needs. The offset is always relative to a stable sentence UUID — if the sentence survives, the offset is valid.
Automation vs. Curation
Should the runtime auto-assign everything (UUIDs, structural parses, sentence boundaries) or allow human curation? Automation scales but is imperfect. Curation is perfect but doesn't scale. The parser's confidence scores are the bridge.
Resolution: Auto-assign with confidence. Allow human overrides on low-confidence nodes. The system records both the auto-parse and any human corrections. Corrections are stored as overlay annotations, not modifications to the parse tree.
Local-first vs. Global Addressability
UUIDs are globally unique but locally scoped — a UUID in my document store means nothing to your document store. Xanadu required a global address space. The Text Runtime doesn't need to solve global addressing — it needs to enable it.
Resolution: Document-scoped UUIDs with a base URL (https://my-docs.example/doc-uuid#node-uuid). Cross-system references use URIs. Within a single system, UUIDs are sufficient. Between systems, the document base URL provides the namespace.

What Would Change Everything

1
Full-Text Semantic Search with Embedding-Based Retrieval
If we could search across document bodies using embeddings — finding paragraphs by semantic meaning, not just exact text — the annotation anchoring system becomes less critical. Users could find content by what it means, not what it says. Annotations could re-anchor by semantic similarity when text changes. Requires: embedding generation for all nodes, a vector index, and a semantic similarity threshold for re-anchoring.
2
Automated Cross-Document Relationship Detection
If the system could automatically detect when two paragraphs in different documents are about the same thing — identifying shared claims, contradictory arguments, complementary ideas — the transclusion and provenance layers could be generated rather than authored. The overlay layer becomes self-populating. Requires: concept extraction, semantic comparison, contradiction detection. This is AI-hard but tractable with modern embeddings.
3
A Global Content Address Space
If content-addressed identifiers (like BendScript's CIDs or IPFS content hashes) became universal, every paragraph on the internet could have a global, verifiable address. Transclusion would work across any document, anywhere. Provenance would be cryptographically verifiable. This is what Xanadu wanted and what the internet still doesn't have. It's an infrastructure problem, not a technical one — but if it happened, the Text Runtime would become a universal layer rather than a per-system runtime.
