Dimension 01

The Convergent Pattern

What pattern did every prior system converge on, and why?

❓

The Question

This is the foundational question. Before designing a pipeline or picking UUID formats, we must understand what every prior system discovered — independently, decades apart, from completely different starting points.

The question matters because the graveyard of prior art is deep. Xanadu (1960), Purple Numbers (2001), SiSU (2006), and BendScript (2024) all solved the same problem with the same architecture — and none achieved escape velocity. Understanding why they converged on the same pattern tells us what's architecturally invariant, and understanding why none fully won tells us what additional ingredients are needed.

The answer, as it turns out, has four layers — and the pattern has been rediscovered at least six times.

🏗️

The Four-Layer Architecture

Every system that solved the problem converged on the same four-layer stack. The layers are:

1
Human Surface
Markdown, plain text, transcripts. Clean, flow-preserving, authored in whatever medium the human chooses. The surface is never polluted with machine identifiers. Writers and readers experience pure text.
2
Parser Pipeline
Format-specific parsers (Markdown, TXT, HTML, DOCX) feed into a format-agnostic structural parser. Produces a typed tree: Document → Section → Paragraph → Sentence. Parsing is best-effort — it never fails, it degrades gracefully.
3
Object Store (Stable Node Tree)
Every node has a UUID v7 — stable forever. Nodes are linked by parent/child/sibling pointers. The store is an index, not a copy — it maps UUIDs to structural positions. The source document remains authoritative.
4
Overlays (Annotations, Links, Tags, Provenance)
Everything that isn't content is an overlay. Annotations reference UUIDs, never positions. Multiple overlays coexist without coordination. This is the applicative pattern — structure applied from outside, never embedded.
"All structure is additive and applicative, rather than tangled inside. This permits many structural variations on the same particular documents and their contents — variations whose cross-connections may in turn be viewed." — Ted Nelson, Xanadu (2000)
📜

60 Years of Independent Discovery

The same four-layer pattern was discovered independently at least six times. Each discovery added a piece of the puzzle:

1960–2000
Xanadu (Ted Nelson)
Origin of the referential model. Invented permanent addresses, content lists (documents as lists of pointers), applicative links (not embedded), and transclusion ("the same content knowably in more than one place"). The vision was complete; the implementation never shipped at scale.
1960s–1970s
Augment / NLS (Doug Engelbart)
Granular addressability in a working system. Every statement in a document had a persistent identifier. Engelbart's team used these identifiers for cross-referencing, annotation, and collaborative work. The precursor to Purple Numbers.
2001–2005
Purple Numbers (Eugene Kim)
The HID vs. NID distinction. Hierarchical IDs (1.5.3) break when content moves. Node IDs (UUIDs) persist. PurpleWiki demonstrated fine-grained transclusion using purple numbers. Proved the concept works in collaborative wiki environments.
2006–2025
SiSU (Ralph Amissah)
Production-grade stable citation numbers. Parses lightweight markup into an abstract object model. Every substantive element gets a stable citation number that survives across output formats (HTML, EPUB, LaTeX, PDF) and translations. 20 years of production use.
2013–present
Hypothesis
Production anchoring at scale. The canonical implementation of fuzzy annotation anchoring. Four-strategy cascading fallback (XPath → offsets → context-fuzzy → exhaustive). Annotations as external overlays, never embedded in the document.
2020–present
Notion, Obsidian, Tiptap
UUID-per-block in production at scale. Notion: every block has a UUIDv4, blocks form a tree. Obsidian: block references and transclusion via ![[Note#^block-id]]. Tiptap UniqueID: stable UUIDs through splits, merges, and collaborative edits.
2024
BendScript
Graph-first document protocol. JSON with content-addressed blocks, typed edges (cites, supports, contradicts, transcludes), and span-level addressing. The most recent re-discovery of the referential document model.
🤝

What Every Implementation Agreed On

Despite different eras, technologies, and use cases, these systems converged on five architectural invariants:

1. Content by Reference, Not by Value
Xanadu · SiSU · BendScript
Documents are lists of pointers to content objects, not character buffers. Editing changes the pointer list, never the content objects themselves. This is how movies have been edited since the 1970s (the Edit Decision List).
2. Stable IDs Assigned at Parse Time
Purple Numbers · Notion · Tiptap
Two kinds of identifiers exist. HIDs (hierarchical, like 1.5.3) are human-friendly but break on move. NIDs (persistent UUIDs) survive everything. The field converged on NIDs as the primary addressing mechanism.
3. Applicative Overlays, Not Embedded
Xanadu · Hypothesis · Semiont
Annotations, tags, links sit outside the content and reference UUIDs. This enables profuse, overlapping, multi-author annotations without coordination. Xanadu's key insight: thousands of overlapping links, created by many users, all coexist.
4. Anchoring is Never Perfect
Hypothesis · W3C · LFCC
Every system learned this. Use strategies with fallbacks: precise selector first, fuzzy selector second, orphan as last resort. Never silently misplace an annotation. Confidence scores are essential.
5. Dual Selectors for Robustness
W3C Web Annotation · Semiont
Store both a precise selector (UUID + offset) and a fuzzy selector (TextQuoteSelector with prefix/suffix). Reconcile at write time. At read time, try precise first; if it fails, fall back to fuzzy. The fuzzy fallback stays on the write side.
🔍

Why None Fully Won

If the pattern is so clear, why isn't it everywhere? Four reasons:

1. Xanadu required a global content address space. Nelson's vision required every byte of text on the planet to have a permanent address. This was technically correct but economically impossible before the internet — and even with the internet, it required centralized address assignment that nobody wanted to pay for.

2. Purple Numbers polluted the reading surface. The original Purple implementation placed numbers in the text. Readers saw "¶ 1.5.3" before every paragraph. The numbers were useful but ugly — they broke the flow state for readers. The lesson: stable IDs must be invisible.

3. SiSU was too tightly coupled to its author's workflow. A single-author tool designed for book publishing. Never became a general-purpose runtime because it prioritized output fidelity (perfect LaTeX/EPUB) over API accessibility.

4. Notion proved it could work at scale — but locked it inside an application. Every block has a UUID, transclusion works, references survive edits. But Notion is a product, not a runtime. You cannot take Notion's block model and use it under your Markdown editor, your AI pipeline, or your annotation system.

The Text Runtime is the first attempt to extract this pattern into a general-purpose layer.

💡

The Key Insight

"Treat text the way an operating system treats files. The OS doesn't understand the meaning of a file. It provides identity, storage, indexing, references, metadata, and resilience. The Text Runtime should provide the same capabilities for natural language. Markdown remains the human interface. The runtime becomes the machine interface."

The operating system analogy is precise: a file system gives every file an inode (a stable identifier), stores metadata separately from content, allows hard links (transclusion), supports permissions and provenance (who created this, when), and survives crashes (resilience). The Text Runtime is exactly this — but for paragraphs and sentences instead of files.
